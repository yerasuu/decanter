# `decanter-hook`

A proxy `Galaxy64.dll` that records achievement unlocks as a GOG game
triggers them, from inside the Wine prefix.

## Why this exists

GOG games with Galaxy integration ship `Galaxy64.dll` and call
`IStats::SetAchievement` on it the moment the player earns something. On
Windows that DLL forwards the unlock over local IPC to the running GOG
Galaxy client, which reports it to GOG.

Under Wine there is no Galaxy client listening. The game still makes the
call, the DLL still accepts it, and the unlock goes nowhere — the game
believes it reported it, and nothing ever did. The DLL being present is
not the same as the integration working.

This sits in between: every export is forwarded to the real DLL
unchanged, except that `Stats()` patches one vtable slot on the way
through so `SetAchievement` passes through us first.

**Nothing is sent anywhere yet.** Unlocks are appended to a JSONL file.
Reporting them to GOG is a separate step.

## Building

Not a workspace member — it only compiles for Windows, so a plain
`cargo build --workspace` on Linux would fail on it.

```sh
cd crates/hook
cargo build --release --target x86_64-pc-windows-gnu
```

Output: `target/x86_64-pc-windows-gnu/release/Galaxy64.dll`.

Tests run under Wine (`.cargo/config.toml` sets the runner):

```sh
cargo test --release --target x86_64-pc-windows-gnu
```

## Installing into a game

In the game's install directory, beside its executable:

1. Rename the game's own `Galaxy64.dll` to `Galaxy64.orig.dll`.
2. Copy this crate's `Galaxy64.dll` in its place.

The proxy resolves the real DLL relative to its own location, so both
files have to stay in the same directory.

To undo, delete the proxy and rename `Galaxy64.orig.dll` back.

## Output

One JSON object per line:

```json
{"unlocked_at":1756223400,"achievement":"ACH_FIRST_BLOOD","product_id":"1090734724"}
```

| Variable | Meaning |
|---|---|
| `DECANTER_ACHIEVEMENT_LOG` | Where to write. Defaults to `decanter-achievements.jsonl` beside the DLL. |
| `DECANTER_PRODUCT_ID` | Recorded in each line so a shared log stays attributable. Optional. |

Both are read from the game's environment, so decanter can set them when
it launches the game rather than configuring anything on disk.

## How the vtable offset was found

`SetAchievement` is slot 8 of `IStats`. That is not inferred from
declaration order — every Galaxy method passes its own name to an
internal logging call, so slot 8's body references the literal
`"SetAchievement"` and a format string reading
`Setting achievement: achievementID=%s, name=%s`.

The full derivation, along with a map of every export, interface and
vtable in the DLL, is in [`docs/galaxy64-abi.md`](../../docs/galaxy64-abi.md),
regenerated by `tools/gen_abi_doc.py`.

## Constraints

Two rules hold throughout the code:

- **Never panic.** A panic unwinding into the game's C++ frames is
  undefined behaviour. The release profile aborts rather than unwinds.
- **Never break the game.** Every call is forwarded whether or not the
  logging worked. A missing log path, an unwritable file, a failed
  `VirtualProtect` — each leaves the game running exactly as it would
  have without the proxy.
